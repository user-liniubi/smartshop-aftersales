# SmartShop AI 项目升级审查报告

> 审查日期：2026-11-23
> 源码基线：`ca79332`
> 审查原则：以当前源码、迁移和测试为准，不把文档描述直接当作已实现功能。

## 1. 当前真实架构

```text
消费者 Streamlit / 客服 Streamlit
              ↓ HTTP
           FastAPI
  认证｜对象权限｜参数校验｜请求 ID
              ↓
      售后受控业务工作流
  ┌──────────┼───────────┬──────────┐
DeepSeek   订单工具     BGE + Chroma  人工接管
意图/槽位   MySQL       政策检索      条件更新
  └──────────┼───────────┴──────────┘
        MySQL 会话 / 工单 / 审计
              ↓
        Redis + Celery 异步索引
```

当前分层：

| 层 | 主要文件 | 职责 |
|---|---|---|
| API | `backend/app/api/` | 认证、路由、HTTP 响应 |
| 工作流 | `backend/app/agent/` | 意图、槽位、状态机、有限工具 |
| 业务服务 | `backend/app/services/` | RAG、订单、资格、工单、人工接管 |
| 数据访问 | `backend/app/repositories/` | SQL 查询和条件更新 |
| 数据模型 | `backend/app/models/` | 表、关系、约束和枚举 |
| RAG | `backend/app/rag/` | 解析、分块、BGE、Chroma |
| Worker | `backend/app/workers/` | Celery 异步索引 |
| 前端 | `frontend/` | 消费者端、客服工作台 |

## 3. 未实现或不足

| 目标能力 | 当前状态 | 差距 |

| 多商品对比 | 未实现 | 缺少对比工具和接口 |
| 实时价格/库存 | 未实现 | 订单有成交金额，商品无实时价格库存 |

## 4. 当前问题

1. `AfterSalesIntent` 和 `AfterSalesAgentService` 绑定售后语义，不能直接承担售前/履约统一路由。
2. 商品表没有规格、价格、库存，售前咨询无法从结构化数据回答。
3. 订单没有物流字段，无法可靠回答物流状态。
4. 工单类型 CHECK 只允许 return/exchange。
5. RAG metadata 没有知识分类维度。
6. 退款资格和金额都是确定性结果，尚无“授权范围内部分补偿”的 Agent 决策。
7. 前端没有商品、优惠、物流和授权配置入口。
8. 固定评测只覆盖售后，没有售前和履约评测。

## 8. 架构冲突与兼容策略

- **保留现有售后状态机**：售前和履约新增独立动作，不删除原状态。
- **保留 `/chat`**：新增业务分支，现有售后接口和响应保持兼容。
- **统一工单**：扩展 `request_type=repair`，不单独建维修 Agent。
- **资格仍确定性**：Agent 只处理授权范围内的部分补偿金额建议。
- **实时事实不入向量库**：商品价格、库存、物流继续查询结构化数据。
- **P0 优先**：先完成售前、物流、维修和知识分类，再实施退款授权。

## 9. 升级顺序

1. P0-A：商品结构化字段与查询工具；
2. P0-B：统一意图和售前/订单/售后路由；
3. P0-C：物流状态与维修类型；
4. P0-D：知识分类与前端入口；
5. P1：退款授权规则、Agent 建议、后端校验和审核报告；
6. P2：优惠授权、检索优化、评测扩展和部署文档。

## 10. 审查结论

现有售后核心链路和安全机制质量较好，应保留并扩展。升级不应重写全部项目，而应先把售后状态机提升为统一客服工作流，再补结构化商品、物流和授权决策。P1 的 Agent 金额决策必须建立在确定性资格和后端上限校验之后，不能替代现有规则。
